    데몬 단일 루퍼 + Gradle 빌드 Implementation Plan¶

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: on-device 데몬을 MainLooper 하나 + 작은 Work 풀 구조의 Kotlin 코루틴 모델로 바꾸고, Gradle이 build/hs.jar를 만드는 정식 빌드가 되게 한다. 와이어 프로토콜은 바이트 단위로 유지.

    Architecture: Looper.loop()를 도는 main 스레드가 MessageQueue.addOnFileDescriptorEventListener(epoll)로 소켓·파이프를 감시하고, 연결마다 Dispatchers.Main 위의 코루틴 하나가 readFrame → dispatch → respond를 suspend로 처리한다. CPU/장시간 binder 작업만 Work 디스패처로 보낸다. 중간 단계에서는 아직 포팅 안 된 블로킹 Java 핸들러를 Legacy 디스패처 + 블로킹 스트림 어댑터로 돌려 매 태스크마다 jar가 동작하게 하고, 마지막에 Legacy를 제거한다.

    Tech Stack: Kotlin 2.2.21 (JVM target 17), kotlinx-coroutines-core/android (최신 안정 1.10.x), Gradle(Kotlin DSL, 기존 wrapper), SDK R8(build-tools/36.0.0/lib/d8.jar), JUnit5 + kotlinx-coroutines-test (JVM 단위 테스트), Python 3 (scripts/wire-smoke.py, 기기 통합 테스트), AVD Medium_Phone(API 36).

    Spec: docs/superpowers/specs/2026-10-25-daemon-looper-gradle-design.md

    Global Constraints¶

    • 와이어 프로토콜(docs/wire.md): verb, 인자, 응답 바이트, uint32 BE length + payload 프레이밍, ERR: 문자열, 스트림 len=0 종결자, __exit__ N 트레일러 — 전부 기존과 동일. MAX_CMD = 256, 위반 시 BAD_ARG:bad-length:<len> 후 연결 종료.
    • 엔트리: dev.handsets.daemon.Main.main(String[]), --port=N(기본 9008), 127.0.0.1 바인드, backlog 8, SO_REUSEADDR, TCP_NODELAY. stdout에 hsd listening on 127.0.0.1:<port> 와 hsd ready (sdk=<N>) 출력 유지.
    • 산출물: build/hs.jar (dex만), --min-api 28, R8 --release. 크기 목표: 기준 jar 대비 +300KB 이내, 초과 시 보고.
    • R8: SDK build-tools/<ver>/lib/d8.jar의 com.android.tools.r8.R8를 JavaExec로 실행. 기본 build-tools 36.0.0, -PbuildTools=로 변경.
    • 루퍼(main)에서 금지: 덤프, 인코딩, Thread.sleep, 블로킹 소켓/파이프 I/O, 상한 없는 binder 호출. 애매하면 Work.
    • 스레드 최종 상태: main + Work 풀(min(4, availableProcessors)) (+ 프레임워크 binder/MediaCodec 스레드). hs-ua는 main looper 시도가 실패할 때만 예외로 허용하고 보고.
    • 이미지/상태 스트림(stream, stream_tilejpeg, state_watch, clip_watch)은 최신 프레임만 유지. stream_h264는 공유 전까지 프레임 무손실 + 연결별 backpressure.
    • 호스트 코드(handsets-cli, handsets-tui, handsets-viewer, bindings/) 수정 금지.
    • 검증 기기: AVD Medium_Phone (API 36, x86_64) 하나. adb: E:\packages\Android\Sdk\platform-tools\adb.exe.

    Review Focus¶

    1. TCP 단편화: 명령 프레임의 4바이트 길이/페이로드가 여러 read로 쪼개져 도착 → 하나의 명령으로 정상 처리. (Task 3 ConnTest.fragmentedFrame)
    2. 스트림 중 클라이언트 강제 종료: stream*/state_watch/logcat/shell 중 소켓이 끊김 → 구독 해제, 서브프로세스 kill, 인코더/VirtualDisplay 해제, 다른 연결 영향 없음. (Task 3 ConnTest.cancelOnEof, Task 9 smoke disconnect_cleanup)
    3. 느린/읽지 않는 클라이언트: 스트림을 열고 읽지 않는 클라이언트가 있어도 다른 연결의 ping p95 < 50ms. (Task 3 ConnTest.latestOnlyReplaces, Task 8 smoke slow_client)
    4. 설치 중 업로드 중단: install size=N 후 N바이트를 다 보내기 전에 끊김 → 세션 abandon, 데몬 정상. (Task 6 smoke install_truncated)
    5. UTF-8 / 경계 길이 명령: CJK clip_set, text, 길이 정확히 256/257 프레임 → 기존과 같은 응답. (Task 4 DispatchTest.cjkAndLengthBounds, smoke 케이스)

    Task 3: 이벤트 루프 코어 (Loop, IoLoop, Conn)¶

    Files: - Create: src/dev/handsets/daemon/Loop.kt, IoLoop.kt, Conn.kt - Test: test/dev/handsets/daemon/ConnTest.kt, test/dev/handsets/daemon/SelectorIoLoop.kt(테스트용 IoLoop 구현)

    Interfaces: - Produces: - Loop.kt: object Loop { val Main: CoroutineDispatcher; val Work: CoroutineDispatcher; val Legacy: CoroutineDispatcher; val scope: CoroutineScope; fun init(main: CoroutineDispatcher = Dispatchers.Main.immediate) } — Work = 고정 min(4, cpu) 데몬 스레드 풀(hs-work-N) .asCoroutineDispatcher(), Legacy = 캐시드 풀(hs-legacy-N, Task 9에서 제거). scope = CoroutineScope(SupervisorJob() + Main + CoroutineExceptionHandler{ 로그 }). init이 Dispatchers.Main 해석 실패 시 Handler(Looper.getMainLooper()).asCoroutineDispatcher("hs-main")로 대체하고 어느 쪽인지 stderr에 hsd dispatcher: main=<kind> 출력. - IoLoop.kt: interface IoLoop { fun watch(fd: FileDescriptor, events: Int, cb: (fd: FileDescriptor, events: Int) -> Int); fun unwatch(fd: FileDescriptor) } (events/반환값 의미는 MessageQueue.OnFileDescriptorEventListener와 동일: EVENT_INPUT=1, EVENT_OUTPUT=2, EVENT_ERROR=4, 0 반환 = 해제). class MessageQueueIoLoop(queue: MessageQueue) : IoLoop. object Fds { fun of(ch: SelectableChannel): FileDescriptor } — Android SocketChannelImpl/ServerSocketChannelImpl의 getFD()를 리플렉션으로 호출. - Conn.kt: class Conn(ch: SocketChannel, io: IoLoop) { suspend fun readInt(): Int; suspend fun readFully(n: Int): ByteArray; suspend fun readChunk(max: Int): ByteArray? /* null=EOF */; suspend fun send(payload: ByteArray) /* 프레임(len+payload) 큐잉, 큐 바이트 > OUT_LIMIT(4 MiB)이면 drain까지 suspend */; suspend fun sendRaw(bytes: ByteArray) /* 길이 접두 없이 */; fun sendLatest(slot: Int, payload: ByteArray) /* 같은 slot의 아직 안 나간 프레임을 교체 */; suspend fun flush(); val job: Job /* EOF/에러/close 시 cancel */; fun close() }. 읽기 EOF는 EOFException을 던진다.

    • [ ] Step 1: 실패하는 테스트 작성 — ConnTest (JVM, SelectorIoLoop가 별도 스레드에서 java.nio.channels.Selector로 IoLoop 계약을 흉내, 디스패처는 단일 스레드 executor):
    • fragmentedFrame: 클라이언트가 [0,0,0,4]를 2바이트씩, "ping"을 1바이트씩 보냄 → readInt()==4, String(readFully(4))=="ping".
    • sendFramesInOrder: send("a"), send("bb") → 클라이언트가 00000001 61 00000002 6262 수신.
    • backpressureSuspends: 클라이언트가 읽지 않을 때 send를 반복하면 누적 큐 바이트가 OUT_LIMIT+최대 프레임 1개를 넘지 않음(초과 시점에 suspend 확인 — withTimeoutOrNull(200){ send(big) } == null).
    • latestOnlyReplaces: 읽지 않는 클라이언트에 sendLatest(0, f1..f50) → 클라이언트가 읽기 시작하면 받은 프레임 수 ≤ 3 이고 마지막이 f50.
    • cancelOnEof: 클라이언트 close → conn.job.isCancelled 가 1초 내 true, 진행 중 readInt()는 EOFException/취소로 끝남.
    • [ ] Step 2: Run: ./gradlew test --tests '*ConnTest*' — Expected: FAIL (클래스 없음).
    • [ ] Step 3: Loop.kt, IoLoop.kt, Conn.kt 구현. Conn은 읽기 대기 시 EVENT_INPUT, 출력 큐가 비어 있지 않을 때만 EVENT_OUTPUT을 watch(쓰기 가능할 때마다 non-blocking write). 소켓은 configureBlocking(false), TCP_NODELAY.
    • [ ] Step 4: Run: ./gradlew test --tests '*ConnTest*' — Expected: PASS.
